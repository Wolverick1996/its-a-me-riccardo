# Core Next.js concepts used in this project

## App Router: folders are routes

Next.js (the "App Router" flavor, which we use) turns the folder structure inside `src/app/` directly into URLs:

- `src/app/page.tsx` → `/`
- `src/app/software/page.tsx` → `/software`

There's no separate route-config file to maintain by hand: create a folder with a `page.tsx` inside it, and the route exists.

## Server Component vs Client Component

Every file under `src/app/` is, by default, a **Server Component**: its code runs only to produce the initial HTML (in our case, during `next build`, since the site is exported statically — see [`docs/03-static-export-github-pages.md`](./03-static-export-github-pages.md)). That code **never ends up in the JavaScript downloaded by the browser**, and it can't use anything that only exists in the browser, like `window`, `localStorage`, or `useEffect`.

A **Client Component** is the opposite: it's regular React code that runs in the user's browser, can react to clicks, use `useState`/`useEffect`, read `window`. To mark one, add the line `"use client"` at the top of the file — that's exactly what we do in [`src/components/redirect/ClientRedirect.tsx`](../src/components/redirect/ClientRedirect.tsx):

```tsx
"use client";

import { useEffect } from "react";
import { useRouter } from "next/navigation";

export default function ClientRedirect({ to }: { to: string }) {
  const router = useRouter();
  useEffect(() => {
    router.replace(to);
  }, [router, to]);
  return null;
}
```

This component **has to** be a client component: `useRouter()` and `useEffect()` only exist in the browser. `router.replace(to)` performs a client-side navigation without leaving an entry in the browser's history (unlike `router.push`, which would — with `replace`, a user who presses "back" from `/software` doesn't land back on the redirect page, which wouldn't make sense to revisit).

## Rendering ahead of time, and hydration

**SSR (Server-Side Rendering)** means generating HTML that's already "full" (with all the text and structure visible) instead of sending the browser an empty page that only fills in after JavaScript has run. In our case, since this is a static export, that HTML isn't generated per request by a server, but **once, during `next build`**, and saved as an `.html` file — the end result is conceptually the same (ready-made HTML), just computed ahead of time instead of on the fly.

**Hydration** is the next step, which happens in the browser: React takes that HTML already present on the page and "attaches" itself to it, treating it as if it had rendered it, so it can update it in response to events (clicks, a `useState` change, etc.) — without having to redraw everything from scratch.

**Hydration mismatch**: if the HTML generated by the server (or by the build, in our case) is _different_ from what React generates the first time it runs in the browser, React notices and flags it as an error (or corrects it abruptly, causing a visible flash). The classic way this happens by accident: using something like `if (window.innerWidth > 768) { ... }` to decide WHAT to render — during build/SSR, `window` doesn't even exist, so the server has no way of knowing the end user's screen width, and the browser will almost certainly generate something different.

This is exactly why, when we implement the switch between the "Desktop XP" shell and the "Metro mobile" shell (see [`src/components/shell/ResponsiveShell.tsx`](../src/components/shell/ResponsiveShell.tsx), milestone 6), we will **not** use `window.matchMedia` to decide which tree to mount, but responsive CSS classes (`hidden md:block` / `block md:hidden`): this way the generated markup is always identical both at build time and in the browser (both trees always exist in the DOM), and only which of the two is _visible_ changes — something CSS can decide without needing to know anything ahead of time.

Quick index back to the real code, so you can see each concept above in context instead of just in the abstract:
