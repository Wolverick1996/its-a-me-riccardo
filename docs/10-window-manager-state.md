# Window manager: Zustand + react-rnd

Real drag/resize ([`useWindowManagerStore.ts`](../src/store/useWindowManagerStore.ts), [`Window.tsx`](../src/components/desktop/Window.tsx)) replaced the placeholder version that only opened/closed/cascaded windows with plain `useState` in `Desktop.tsx`.

## What these two libraries actually are

[Zustand](https://zustand.docs.pmnd.rs/) is a small state-management library for React — an alternative to reaching for `useState`/`useContext` when a piece of state needs to be read and written from components that don't have a parent/child relationship to pass props through. `create((set, get) => ({ ...initialState, someAction: () => set(...) }))` returns a hook; any component that calls it re-renders when the store changes. What actually makes it useful here rather than just "yet another way to hold state" is that a component can subscribe to a _slice_ of the store instead of the whole thing (`useWindowManagerStore((state) => state.windows[app.id])` in `Window.tsx`) — that component only re-renders when its own window's data changes, not every time any window anywhere moves. That matters a lot with several draggable windows sharing one store: without slicing, dragging one window would re-render all of them on every pointer-move.

[react-rnd](https://github.com/bokuweb/react-rnd) is a "resizable and draggable" wrapper component — wrap anything in `<Rnd>` and it becomes a real pointer-driven box: it listens for pointer events itself and, as the user drags a handle or an edge, calls back with the new position/size (`onDragStop`, `onResizeStop` below). It doesn't hold that state itself, though — it's a controlled component, driven by the `position`/`size` props passed in each render, the same as a controlled `<input>`. Deciding what to _do_ with the numbers it reports (here, writing them into the Zustand store) is entirely up to whoever uses it.

## Why a Zustand store instead of lifting state further up

Before, `Desktop.tsx` owned all window state and passed callbacks down. That stops working once a window's own drag/resize needs to write geometry back — `Window.tsx` is what `react-rnd` lives inside, so it's the one calling `onDragStop`/`onResizeStop`, not `Desktop.tsx`. Rather than thread geometry updates back up through props, both components read and write the same [Zustand](https://zustand.docs.pmnd.rs/) store directly: `Desktop.tsx` for which windows exist and in what order, `Window.tsx` for its own geometry, focus, and minimize/maximize state.

## Window geometry becomes real pixel numbers, not a live `calc()` string

Every other scaled value in this shell is a CSS `calc(<reference px> * var(--xp-scale))` string (see [docs/08-dpi-scaling.md](./08-dpi-scaling.md)) — it never needs JavaScript, and it re-computes for free on resize. `react-rnd` can't work that way: it needs actual numbers for `position`/`size`, because dragging and resizing produce real pixel deltas it has to add to something. So a window's size is converted out of "reference px" into real pixels exactly once, when it's opened (`readScale()` reads `--xp-scale` off the DOM at that moment) — after that, its geometry is just plain numbers in the store, the same as any real OS window. This does mean an open window no longer rescales itself if the browser is resized afterward, unlike the rest of the shell — but that's authentic, not a bug: a real window doesn't resize itself when you plug into a different monitor either, only when you drag it yourself.

## Taskbar buttons are a three-way toggle, not just "focus"

Clicking a taskbar button and clicking a window to focus it aren't the same action. Real XP's taskbar button, clicked on the already-focused window, minimizes it instead — clicked on a minimized one, restores it. That's `selectFromTaskbar`, kept as a separate store action from the plain `focusWindow` a window's own `onMouseDown` uses, so clicking inside a window can never accidentally minimize it.

## Explicit z-index per window instead of relying on DOM order

Windows used to stack purely by DOM order — the focused one moved to the end of a render list, painting it on top. Each window now carries its own numeric `zIndex` in the store instead, bumped on open/focus, independent of where it sits in the DOM; `.taskbar` and `.start-menu` get a fixed `z-index` far above any window's for the same reason, since neither is guaranteed to be the last thing painted anymore either.

## Minimize/maximize animate a wireframe outline, not the real window

An earlier version of this shell animated the real window itself — fading and scaling the actual `.window` box with a CSS transition. That's not what classic Windows (XP included) actually does, and it's not just a stylistic choice: pre-DWM Windows had no compositor, so it had no cheap way to redraw a whole window's real content smoothly dozens of times over 150–200ms. Instead it faked the zoom with a plain 1px outline rectangle — no fill, nothing rendered inside it — interpolating between two geometries, while the real window snaps in or out **instantly** at either end. That's true for all four transitions this shell animates, not just minimize: minimizing, restoring from the taskbar, maximizing, and restoring back down from maximized all get the same wireframe treatment ([`xpWireframeAnimation.ts`](../src/lib/xpWireframeAnimation.ts)); only closing a window has no animation at all, wireframe or otherwise.

`animateWireframe(from, to, container)` creates a `.xp-wireframe` div, sets it to `from`'s geometry, forces a reflow so the browser has actually painted that starting position, then sets it to `to`'s geometry on the next frame — CSS's `transition: all 180ms linear` (see `desktop-shell.css`) does the actual interpolation between those two states. `Window.tsx` hides the real window (`display: none`, no transition) for the whole time this runs, then shows it again — already in its final position/size — the instant the wireframe finishes. `container` is always the `.win-xp-shell` root, so the wireframe stays scoped under the same selector prefix as the rest of the shell's CSS and sits inside the stacking context its `z-index` is relative to.

Minimize and restore both react to the store's `isMinimized` flag changing (from `Window.tsx`'s own button, or `selectFromTaskbar` toggling it from the taskbar — either path needs the same animation), in a `useEffect` that measures the window's own stored geometry and its taskbar button's real `getBoundingClientRect()` (found via a `data-window-id` attribute in `Taskbar.tsx`) and animates a wireframe between them. Maximize/restore-down work the same way but are triggered directly from the button's own click handler instead, since nothing else can toggle `isMaximized`: it measures the window's current geometry against `desktopWorkArea()` (maximizing) or `win.restoreGeometry` (restoring down, using the same pre-maximize geometry `toggleMaximize` already stashes in the store for its own instant-snap use), runs the wireframe, and only then calls `toggleMaximize` — so the real window's layout update lands exactly when the wireframe finishes, not before.

An earlier version of this doc claimed maximize/restore-down don't animate at all in real XP, reasoning from a frame-by-frame `getBoundingClientRect()` log of the real window that showed no intermediate sizes. That was true of what it measured — the real window's content really does snap, never stretches — but wrong about the whole picture: the wireframe is a separate element the real window's own rect never reveals, so measuring only the real window can't see it.
